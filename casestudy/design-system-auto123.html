Introduction

Auto123 is a car marketplace for European buyers and sellers, starting with Lithuania. The founders saw an opportunity in a market where existing platforms were missing important features and offered poor user experiences. I was brought in to turn their initial product concept into the full web and iOS experience.

Starting with a Vibe-coded prototype

The founders had already mapped out their ideas in a vibecoded prototype. It was never launched or used by customers. I used it as the starting point, then worked through the product from the ground up, refining the UX, defining the interface, and designing the responsive web and iOS experiences.

Why a design system was needed

Web and iOS needed shared foundations despite having different visual styles.
Every product component needed to come from one source of truth.
Semantic tokens made choosing colors and styles more intuitive.
The large number of screens made reusable components essential.
The system had to evolve alongside the product as new patterns emerged.
Support the planned AI assisted development workflow.

The design System

I built the system entirely from scratch, starting directly from the product’s real interface needs rather than adapting templates or existing design systems. Every component was created and standardized as the need arose through actual product work.

Style Guide

Colour

I kept the palette small, but made each colour scale intentionally uneven. This gave me more useful stops for semantic tokens without filling the system with shades I would never use. The primary colours came from the client's existing logo. I added a secondary colour to give the interface more visual aesthetic range

Typography

I wanted a bold typeface with a variable font so future web animation would be easier to handle. Overused Grotesk gave me the contrast and character I wanted. It is also free for commercial use, which made it a practical and sustainable choice for the project.

Icons

I chose an open source icon library with active support. Keeping the icons in a ready-made library meant development could use the same set without having to export assets individualy

Shadows

I kept shadows to a minimum. In an information-dense product, clear outlines and backgrounds should do most of the visual separation. Shadows are reserved for states where elevation is actually useful like menus and hover interactions.

Keeping Design System and Product in Sync

Once the foundations were in place, I started designing the actual product and built the system alongside it. When a new component was needed, I added it to the library, published it, and used the library version in the product. Keeping the product tied to the main components meant I could update a component once and propagate the change across every use case. I also used Push to main component when improving individual variants, which kept the system and product in sync as the work evolved.

Based on the founders' data, most customers were expected to use the mobile app, while the web product would be used more heavily by dealers, so theme switching wasn't a priority for the web experience.

The iOS Layer

Once the web experience was in place, I moved to the iOS app. It needed a more native visual language with modern iOS aesthetics while still feeling recognisably Auto123. This was where the flexibility of the system really paid off. The foundations were robust enough to support a completely different visual layer without rebuilding the system from scratch. I created new iOS tokens from the existing primitives, then added a dedicated set of components for the iOS experience.

Handoff

The full library was handed over to the client and is now being used alongside the product in development. The engineering team connected the system to their AI workflow through Figma MCP, so the coded version can stay aligned with the design system and updates are a prompt away.

Takeaway

The system made product design roughly 2× faster while keeping the work cohesive as the product grew. That saved time also helped the team move into development sooner. The scope didn't cover motion or micro-interactions, so those were left to platform defaults. For future systems, I'd extend the same thinking into motion tokens that define things like page transitions, touch responses, and hover behaviour. Motion is another place where a product can build a recognisable character.
